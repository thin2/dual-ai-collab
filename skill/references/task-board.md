# 任务板格式规范

## 任务板文件路径

`planning/tasks.json` 是真相源；`planning/codex-tasks.md` 是同步渲染的任务定义。
运行 `board show` / `board show --json` 查看实时聚合面板。

## 任务板头部

```markdown
# Codex 任务板 - [功能名称]

**创建时间**: YYYY-MM-DD HH:MM:SS
**规范文档**: planning/specs/YYYYMMDD-HHMMSS-[功能名称].md
**总任务数**: X
**预计总工时**: X 小时
```

## 单个任务格式

```markdown
## 任务 #001: [任务标题]

**优先级**: P1
**状态**: OPEN
**分配给**: Codex
**创建时间**: YYYY-MM-DD
**预计工时**: X 小时
**依赖任务**: 无
**执行级别**: normal
**卡死阈值**: 5m
**完成时间**: -
**Codex审查**: 未审查
**Claude审查**: 未审查
**审计评分**: -
**审计意见**: -

### 任务描述
[详细描述任务内容]

### 技术要求
- [技术要求 1]
- [技术要求 2]

### 验收标准
- [ ] [验收标准 1]
- [ ] [验收标准 2]

### 相关文件
- `path/to/file1.py`

---
```

## 任务拆分原则

- 每个任务 1-3 小时完成
- 任务之间尽量独立
- 优先级明确（P1 > P2 > P3）
- 验收标准清晰
- 为长任务标记合适的执行级别或卡死阈值

## 可执行验收命令

为了支持自动验证，建议在 `### 验收标准` 中至少写一条带反引号的可执行命令。例如：

```markdown
### 验收标准
- [ ] `python skill/scripts/cli.py summary` 可正常执行
- [ ] `python -c "import mymodule"` 不报错
- [ ] 页面功能符合产品要求
```

规则：

- 脚本只会提取带反引号的命令，例如 `` `bash tests/run_all_tests.sh` ``
- 纯文字验收标准会被保留给人工审查，但不会被自动执行
- 如果一个任务没有任何可执行验收命令，`verify_task.sh run` 会返回 `NO_VERIFICATION_COMMANDS`
- 优先使用 `python`、`npm`、`pytest` 这类跨平台命令；显式写 `bash xxx.sh` 时，Windows 需要额外安装 Git Bash 或 WSL

## 依赖任务字段说明

- `**依赖任务**: 无` — 无依赖，可随时执行
- `**依赖任务**: #001` — 依赖单个任务
- `**依赖任务**: #001, #002` — 依赖多个任务，所有列出的任务都必须完成

依赖检查规则：必须有与当前任务定义和执行轮次匹配的集成记录，目标提交仍在目标仓库 HEAD 历史中，且集成验收报告通过。旧 DONE / VERIFIED 不会自动解锁。

`**依赖任务**` 中出现的每个 `#编号` 都是硬依赖，`select` 不会领取依赖未完成的任务。

如果两个任务只依赖接口契约、可以 Mock 先行并行开发，使用扩展字段：

- `**接口依赖**: #001（基于契约 Mock 先行）` — 仅作说明，不参与调度

并另建一个对两端都硬依赖的集成任务。详见 [execution-optimization.md](./execution-optimization.md) 第 3 节。

## 执行级别与卡死阈值

- `**执行级别**: quick` — 轻量任务，默认卡死窗口 3 分钟
- `**执行级别**: normal` — 常规任务，默认卡死窗口 5 分钟
- `**执行级别**: heavy` — 重任务，默认卡死窗口 10 分钟
- `**卡死阈值**: 8m` — 显式覆盖执行级别对应的默认值

推荐规则：

- 能用 `执行级别` 表达时，优先使用 `执行级别`
- 只有任务确实需要特殊处理时再显式写 `卡死阈值`
- 旧任务板未写这两个字段时，默认按 `quick` 处理（3 分钟）

## 状态流转

```
OPEN → IN_PROGRESS → AWAITING_REVIEW → AWAITING_INTEGRATION → DONE
                           ↓
                       REJECTED → 修复 → 重新验收与审查

```

## 审查字段说明

- `**Codex审查**`: Codex 代码审查结果（未审查 / PASS / FAIL + 评分）
- `**Claude审查**`: Claude 最终审查结果（未审查 / VERIFIED / REJECTED + 评分）
- 修复后两个审查字段重置为"未审查"，重新走完整审计流程

## 面板与交付证据

`board show` 分别显示任务阶段、执行结果、验收、审查、集成和下一步。运行记录和验收报告从 `.dual-ai-collab` 读取，任务 JSON 只保存任务定义与人工审查/集成凭据。查看 Markdown 老任务板时不会自动迁移写入 JSON。

- `run complete 001`：在执行目录验收，成功仅进入待审查。
- `board review 001 --decision approved --note "审查结论"`：记录主模型/人工审查。拒绝用 rejected。
- `board integrate 001 --target /source --commit SHA --note "该提交包含任务改动"`：要求目标工作区干净、提交已经进入 HEAD，并在目标目录重新验收。不自动合并或提交。
- 新轮次、任务范围变更、重新验收或手动改变状态会让旧凭据失效。
- 集成命令检查提交可达性和验收结果；审查者仍须确认指定提交实际包含本任务改动，不会自动证明代码语义等价。
- 非 Git 项目可继续执行/审查，当前不能通过自动集成确认解锁硬依赖。

`board context 001` 导出不超过 64 KiB 的上下文；包含任务章节、规范引用、依赖和验收，不递归读取文件或历史日志。额外约束、决策与相关文件应维护在任务章节中。
