# 执行阶段优化指南

## 1. 任务中检查点

### 原流程问题

"领取 → 实现 → 验收 → 标记 DONE" 是线性的。任务卡住时才发现规划问题，返工成本高。

### 优化流程

#### 1.1 任务启动检查（Kickoff Check）

**时机**：任务状态改为 `IN_PROGRESS` 后，实现前立即做。

**执行者**：Claude（无论是 direct/adapter/Claude-only 模式）

**流程**：
1. 读任务描述、验收标准、相关文件列表
2. 快速判断：描述是否充分？技术方向是否明确？有没有歧义？
3. 如果发现问题，立即询问用户或补充说明

**检查清单**：
- [ ] 任务目标一句话能说清吗？
- [ ] 相关文件都列了吗？有没有遗漏的文件？
- [ ] 验收标准是否可验证？有没有定性标准？
- [ ] 依赖任务都完成了吗？
- [ ] 技术方案有指导吗？还是要自主设计？
- [ ] 有没有明显的冲突项或风险未记录？

**输出**：
```
## Kickoff Check
- 任务理解：CLEAR / UNCLEAR
- 需补充的信息：[无 / 列表]
- 建议的技术方向：[简述]
- 预期卡点：[无 / 列表]

建议立即启动 / 需先澄清问题
```

**典型发现**：
- "验收标准'功能正常'太定性，应该改为'支持 X、Y、Z 三个场景'"
- "依赖的 API 文件在 #001，但 #001 还没完成"
- "这个改动会影响现有的权限系统，需要确认是否考虑了兼容性"

#### 1.2 任务中期检查（Midpoint Check）

**时机**：任务预计工时过半（如 2h 任务，1h 后）或收到 stall 信号时。

**执行者**：Claude 或自动检测（若有 stall detection）

**流程**：
1. 查看执行状态：`cli.py run status XXX`、日志尾部、已改动文件（Claude-only 模式下自查）
2. 如果有卡点，判断是：
   - 技术困难（需要技术建议）
   - 需求歧义（需要澄清）
   - 环境问题（需要修复环境）
   - 规划遗漏（需要回到规划阶段）
3. 针对性给出建议或决策

**决策树**：
```
任务中期无进展或遇到困难
  ├─ 是否能在 15 分钟内解决？
  │  ├─ YES → 给技术建议，继续
  │  └─ NO → 进入下一步
  └─ 根本原因是什么？
     ├─ 需求歧义 → 立即澄清或返工规划
     ├─ 技术路线冲突 → 提供 2-3 个方案，让用户选
     ├─ 环境缺失 → 补环境，重试
     └─ 规划本身有问题 → 升级为规划审计，考虑取消或改期
```

**输出**：
```
## Midpoint Check
- 当前进度：[百分比 / 描述]
- 遇到的困难：[无 / 描述]
- 根本原因分类：[技术 / 需求 / 环境 / 规划]
- 建议的处理方式：[继续 / 澄清 / 换方案 / 返工规划 / 取消任务]

如需决策，向用户确认
```

#### 1.3 最终验收检查（Final Acceptance）

标准流程不变，但加强对"验收标准覆盖"的检查：
- 可执行的验收命令都通过了吗？
- 定性标准也人工确认了吗？
- 有没有遗漏的边界情况？

如果这里发现问题，回到 1.2 中期检查的决策树处理。

### 配置建议

在任务板中可选加入：
```markdown
## 任务 #001: [标题]

**预计工时**: 2 小时
**中期检查点**: 1 小时后（或开发者自行判断）
**预期主要风险**: [无 / 列表]

### 任务描述
...

### 验收标准
...
```

## 2. 修复决策框架

### 原流程问题

现在只说"修复上限 3 次"，但没有说修复失败后怎么决策。容易陷入无限循环。

### 优化流程

#### 2.1 修复前的根因分析

**触发**：审计反回为 REJECTED 后。

**执行**：Claude 先分析问题根源，不是直接返回问题清单。

**分类**：
```
1. 理解偏差型
   - 开发者误解了需求或验收标准
   - 修复成本：低（通常 15-30 分钟）
   - 处理：直接返回更清晰的说明 + 修复清单

2. 设计缺陷型
   - 任务描述本身有漏洞或冲突
   - 修复成本：中（通常 1-2 小时）
   - 处理：回退到规划审计，补充或修改规划

3. 环境问题型
   - 依赖库缺失、API 不可用、配置错误
   - 修复成本：中（通常 30-60 分钟）
   - 处理：先修环境，再重试

4. 技术困难型
   - 实现方案有技术障碍（如性能、兼容性）
   - 修复成本：高（通常 2+ 小时）
   - 处理：提供替代方案或降级需求

5. 无法修复型
   - 问题触及系统架构或第三方 bug
   - 修复成本：极高或不可行
   - 处理：任务标记 FAILED，记录阻塞项
```

#### 2.2 修复决策矩阵

```
修复轮次 | 根因类型 | 处理方式 | 重试阈值
---------|---------|---------|----------
第 1 次  | 理解偏差 | 返回清晰说明，直接重试 | 无阈值
第 1 次  | 设计缺陷 | 回规划审计 | 需用户确认
第 1 次  | 环境问题 | 修环境后重试 | 1 次尝试
第 1 次  | 技术困难 | 提供方案选项 | 需用户选择
第 1 次  | 无法修复 | 标记 FAILED | 不重试
---------|---------|---------|----------
第 2 次  | 理解偏差 | 升级为标准审计 | 最后 1 次
第 2 次  | 设计缺陷 | 修改规划后重试 | 最后 1 次
第 2 次  | 环境问题 | 标记 FAILED（环境问题） | 不重试
第 2 次  | 技术困难 | 标记 FAILED（技术困难） | 不重试
---------|---------|---------|----------
第 3 次  | 任何类型 | 标记 FAILED | 不重试
```

#### 2.3 修复清单格式

返回给开发者的修复清单，必须按优先级 + 根因分类：

```markdown
## 修复清单 - 任务 #XXX（第 N 轮）

### 根因分类
[理解偏差 / 设计缺陷 / 环境问题 / 技术困难]

### 高优先级问题（必改）
1. [问题] - [根因] - [修复方式]
2. [问题] - [根因] - [修复方式]

### 中优先级问题（应改）
1. [问题] - [根因] - [修复方式]

### 低优先级建议（可改）
1. [建议]

### 修复验证方式
- 运行命令：[命令]
- 人工检查：[清单]

### 下一步
- 如果修复失败第 2 次，会升级为标准审计或标记 FAILED
- 预计修复工时：[X 小时]
```

#### 2.4 修复成本超过重做时

如果发现"修复成本 > 重做成本"，直接建议：
```
## 成本评估

修复这个任务需要：
- 重新理解需求：30 分钟
- 调试技术问题：2 小时
- 验证修复效果：30 分钟
**总计：约 3 小时**

重新做一遍此任务：
- 理解需求：10 分钟（基于现有规划）
- 新实现：1.5 小时
- 验证：30 分钟
**总计：约 2 小时**

**建议**：废弃这次修复，重新做一遍（节省 1 小时）
```

## 3. 并行开发策略

### 原流程问题

任务有依赖关系时，下游任务必须等上游完成。但实际上可以"基于预期接口"提前开始。

### 优化流程

#### 3.1 依赖分类

```
强依赖（必须等）：
- 上游产出的数据/配置/密钥被下游直接使用
- 例：API 实现完成后才能开发前端页面调用

弱依赖（可提前）：
- 上游和下游有明确的接口约定，但实现独立
- 例：前端可以基于 API 文档提前开发，用 Mock 服务
```

#### 3.2 "Mock 先行"方案

**关键约束**：`select` 脚本会把 `**依赖任务**` 中出现的每个 `#编号` 都当作硬依赖，依赖未 DONE 时任务不会被领取。所以：

- 强依赖 → 写进 `**依赖任务**`
- 弱依赖 → **不要**写进 `**依赖任务**`，改写到扩展字段 `**接口依赖**`（脚本会原样保留但不参与调度）
- 集成验证 → 单独拆成一个任务，对两端都是强依赖

**任务板写法**：

```markdown
## 任务 #001: API - 用户列表接口

**优先级**: P1
**依赖任务**: 无

### 接口契约
- `GET /api/users?page=&size=` → `{ items: User[], total: number }`
- 错误：401 / 403 / 500，统一 `{ code, message }`

---

## 任务 #002: 前端页面 - 用户列表

**优先级**: P2
**依赖任务**: 无
**接口依赖**: #001（基于契约 Mock 先行）

### 技术要求
- 使用 `mock/users-list.json`，格式严格按 #001 的接口契约
- 数据请求集中在一个 service 文件，便于后续切换真实接口

---

## 任务 #003: 集成 - 用户列表联调

**优先级**: P2
**依赖任务**: #001, #002
**执行级别**: quick

### 验收标准
- [ ] 前端去掉 Mock，改调真实接口
- [ ] `npm test` 通过
- [ ] 空列表 / 401 / 500 场景前端表现正确
```

**执行**：
1. #001 和 #002 都无硬依赖，`select --parallel` 可同时领取
2. #002 按契约用 Mock 实现
3. 两者 DONE 后 #003 自动解锁，做联调

**前提**：接口契约必须在规划阶段写清楚（字段、类型、可空性、错误格式）。契约写不清的，不要拆成弱依赖，老老实实写硬依赖。

#### 3.3 集成任务验收清单

集成任务（如上例 #003）的验收至少覆盖：

- 接口匹配：字段名、类型、可空性、分页结构与契约一致
- 错误对接：后端每种错误码在前端都有对应表现
- 端到端：核心路径至少一条可执行验证命令
- Mock 清理：Mock 文件和开关已移除或仅在测试环境生效

集成失败时，按 [修复决策框架](#2-修复决策框架) 判断是哪一端的问题，打回对应任务而不是在集成任务里硬改。

## 4. 审计缺陷模式库

### 原流程问题

审计反馈是"这个代码有问题"，但没有记录"这类问题为什么频繁出现"。难以持续改进。

### 优化流程

#### 4.1 缺陷模式文件

由 Claude 在审计时手工维护（目前没有脚本自动统计），文件：`planning/defect-patterns.md`

```markdown
# 缺陷模式库

| 模式 ID | 名称 | 出现次数 | 涉及任务 | 预防检查项 |
|---------|------|---------|---------|-----------|
| boundary | 边界处理缺失 | 3 | #002, #005, #007 | 空值/空列表/0/极大值是否处理？ |
| concurrency | 并发不安全 | 1 | #004 | 同一资源并发修改是否加锁或幂等？ |
| vague-acceptance | 验收标准定性 | 2 | #003, #006 | 每条验收标准能否用命令或具体场景验证？ |
| error-path | 错误路径缺失 | 0 | - | 依赖超时/失败时状态是否一致？ |
```

初始可只放上面几类常见模式，审计中遇到新类型再加行。

#### 4.2 审计报告中标记模式

审计报告的每个问题后追加模式 ID：

```markdown
### 发现的问题
1. 删除接口未检查空列表 — 模式：boundary（本项目第 3 次）
2. 缓存写入无并发保护 — 模式：concurrency（本项目第 1 次）
```

审计完成后，同步更新 `planning/defect-patterns.md` 的次数和涉及任务。

#### 4.3 升级规则

- 某模式累计 **≥ 3 次**：后续任务的 Kickoff Check 加入该模式的预防检查项
- 某模式累计 **≥ 3 次**且属于高风险类（concurrency、安全相关）：后续相关任务的轻审计升级为标准审计
- `vague-acceptance` 累计 ≥ 2 次：说明规划阶段有系统性问题，下一批规划时在 3.2 设计质疑中重点检查验收标准

#### 4.4 恢复与续用

`planning/defect-patterns.md` 是普通规划文件，对话压缩或中断后按 [recovery.md](./recovery.md) 恢复时一并读取即可。

## 使用建议

| 优化项 | 默认 | 说明 |
|-------|------|------|
| Kickoff Check | 所有任务都做 | 成本低，主要拦截描述不清的任务 |
| Midpoint Check | heavy 任务 / 出现 stall 时 | 其余任务可跳过 |
| 修复决策框架 | 每次 REJECTED 都走 | 防止返工无限循环 |
| Mock 先行并行 | 有清晰接口契约的前后端任务对 | 契约不清就用硬依赖 |
| 缺陷模式库 | 任务数 ≥ 5 的项目 | 小项目收益不明显，可跳过 |
