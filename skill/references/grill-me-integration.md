# grill-me 对抗性质疑集成指南

本文档说明如何在双 AI 协作流程中集成 `grill-me` 对抗性质疑机制。

## 重要说明

**grill-me 是可选的增强，不是必需依赖。** 所有流程都有降级方案：
- **有 grill-me**：用 grill-me Prompt
- **无 grill-me**：Claude 手工执行同等思路（见各步的"降级方案"）

## 核心思想

`grill-me` 的作用是暴露隐藏假设、质疑设计决策、找出遗漏的边界情况。与其说"查清单"，不如说"故意挑刺"。这样做的目的是在规划和审计阶段提早发现问题，而不是在开发或测试中才暴露。

## 集成点

### 1. 访谈后期（第 2-3 轮对中等/复杂需求）

**时机**：用户目标基本清晰后，进入细节讨论。

**目的**：暴露隐藏假设、技术风险、边界情况。

**流程**：
1. Claude 完成第一阶段访谈（澄清核心需求）
2. Claude 调用对抗性提问（grill-me 或手工）
3. 对方输出 5-10 个深度追问
4. 用户回答这些提问
5. Claude 综合所有信息生成需求规范

**有 grill-me 时**：调用下方 grill-me 对抗性提问 Prompt

**无 grill-me 时**：Claude 手工执行 [prompt-templates.md](./prompt-templates.md) 1.5 的对抗性提问，输出格式相同

#### grill-me 对抗性提问 Prompt

```text
你是对抗性需求评审员。用户的需求是：[需求简述]

当前已确认的信息：
- [维度 1]
- [维度 2]
- [维度 3]

请从以下维度各提 1-2 个"故意挑刺"的问题，用来暴露隐藏假设和风险：
1. 功能边界：如果用户这样做呢？那样做呢？
2. 技术可行性：有没有隐藏的技术债或性能陷阱？
3. 数据安全：数据流经哪些地方？如果被拦截呢？
4. 用户流程：如果用户不按预期操作呢？
5. 集成风险：与现有系统的冲突点在哪里？
6. 成本权衡：为了快速上线，可以牺牲什么？

输出格式：
## 功能边界
1. [问题]
2. [问题]
## 技术可行性
1. [问题]
2. [问题]
（以此类推）
```

**典型发现**：
- "登录是否支持第三方 OAuth，还是只有内部账户？"
- "如果并发 10000 用户，系统还能响应吗？"
- "删除数据后，日志/备份中是否需要清理？"
- "国际化需要支持多少种语言？"

### 2. 规划审计中期（审查设计决策）

**时机**：Claude 完成规范符合性审计后，进入"设计质疑"阶段（复杂/高风险需求推荐）。

**目的**：从架构、可维护性、风险角度质疑规划。

**流程**：
1. Claude 完成规格文档和任务板
2. Claude 自审：任务拆分合理吗？验收标准清晰吗？
3. 调用对抗性设计质疑（grill-me 或手工）
4. 对方输出设计缺陷、任务拆分问题、风险预测
5. Claude 决策：直接通过，还是补充规划，还是让用户确认

**有 grill-me 时**：调用下方 grill-me 设计质疑 Prompt

**无 grill-me 时**：Claude 手工执行 [prompt-templates.md](./prompt-templates.md) 1.3 的设计质疑，输出格式相同

#### grill-me 设计质疑 Prompt

```text
你是对抗性设计评审员。请从"能不能稳定交付、能不能维护"角度质疑以下规划：

<context>
规格文档：[路径]
任务板：[路径]
项目路径：$(pwd)
</context>

<focus>
重点质疑：
1. 任务粒度是否合理？有没有任务过大（>3h）或过小（<30m）？
2. 依赖关系有没有隐藏的循环或长链？
3. 验收标准是否真的可测？有没有定性标准难以评判？
4. 边界情况是否覆盖充分？有没有易漏掉的场景？
5. 前后端的协作点是否明确？有没有集成风险？
6. 风险记录是否充分？有没有"已知会失败但没有方案"的点？
</focus>

<output>
## 任务拆分风险
1. [风险描述] - [影响哪个任务]
（没有则写"无"）
## 验收标准问题
1. [问题] - [如何改进]
（没有则写"无"）
## 边界情况缺口
1. [场景] - [应在任务 #XXX 补充]
（没有则写"无"）
## 依赖关系疑虑
1. [问题] - [建议调序或拆分]
（没有则写"无"）
## 整体评估
[规划是否 READY_FOR_DEVELOPMENT 还是 NEED_REFINEMENT，以及建议]
</output>
```

**典型发现**：
- "任务 #005 依赖 #001、#002、#003，如果 #002 延期会卡住整条链"
- "验收标准'用户体验良好'无法自动验证，需要改为具体场景"
- "登录后的数据同步没有说明超时处理，容易留坑"
- "任务 #008 既要前端改，也要后端改，但没有明确的协作点"

### 3. 轻审计升级（对抗性挑战）

**时机**：小型 P3 任务完成后。

**目的**：轻量但有针对性地质疑实现，避免漏掉明显问题。

**流程**：
1. 任务标记为 DONE，验收命令通过
2. 调用对抗性代码挑战（grill-me 或手工，可选）
3. 对方快速指出 3-5 个可能的问题
4. Claude 决策：通过审计，还是升级为标准审计

**有 grill-me 时**：调用下方 grill-me 代码挑战 Prompt

**无 grill-me 时**：Claude 手工执行 [prompt-templates.md](./prompt-templates.md) 3.0 的代码挑战，输出格式相同

#### grill-me 代码挑战 Prompt

```text
你是轻量代码挑战员。请快速指出以下任务代码中的明显缺陷，不需要深入代码评审。

<task>
任务编号：#[XXX]
任务标题：[标题]
相关文件：
- [路径 1]
- [路径 2]
</task>

<acceptance>
- [ ] [标准 1]
- [ ] [标准 2]
- [ ] [标准 3]
</acceptance>

<focus>
请找出 3-5 个"如果是我，我会怀疑这个点"的问题：
1. 边界情况：空值/空列表/零值处理？
2. 错误处理：如果依赖服务超时/失败呢？
3. 并发：如果两个请求同时进来呢？
4. 性能：这段逻辑在大数据量下会卡吗？
5. 一致性：如果中间失败，状态/缓存是否正确？
</focus>

<output>
## 可能的问题
1. [问题描述] - [建议检查的代码区域]
2. [问题描述] - [建议检查的代码区域]
（没有则写"无"）
## 建议
[直接通过审计 / 升级为标准审计 / 提醒开发者检查特定区域]
</output>
```

**典型发现**：
- "删除接口没有软删除标记，后续无法恢复"
- "循环中调用 API，没有考虑速率限制"
- "缓存键没有版本号，新上线代码可能读到旧数据"

## 启用与降级

### 环境检查

```bash
# 检查 grill-me 是否可用
which grill-me && echo "AVAILABLE" || echo "MISSING"
```

### 全流程可选

所有集成点都支持两种模式：
- **有 grill-me**：调用 grill-me Prompt（性能好，输出一致）
- **无 grill-me**：Claude 手工执行同等思路（性能稍差，但完全功能等价）

无需手动切换，Claude 自动根据 skill 可用性判断。

### 禁用方式

如果用户偏好轻流程或环保考虑：
- 简单需求全部跳过对抗性提问
- 中等需求只在规划审计阶段用（降低访谈复杂度）
- 复杂需求按需启用

所有流程向后兼容，不会阻塞工作流。

## 与其他工具的关系

| 工具 | 角色 | 互补方式 |
|------|------|---------|
| `ui-ux-pro-max` | 前端设计规范 | 不冲突；前端复杂时可同时用 |
| `superpowers` | 深度审查（spec/code quality） | grill-me 是轻量质疑，superpowers 是系统性审查；可叠加 |
| `systematic-debugging` | 卡死根因调查 | grill-me 用于规划防雷，debugging 用于运行时救火 |

## 最佳实践

1. **不要过度使用**：grill-me 是"对抗性提问"，不是"完整审查"。用在关键决策点。
2. **用户必须回答**：访谈中的对抗性提问，必须给用户回答的机会。不要硬压规划。
3. **升级而非替代**：发现问题后，可升级为完整审计或让用户确认，不是自动解决。
4. **记录决策**：规划中的对抗性提问和答案要写入需求规范，作为后续审计和返工的依据。
5. **保持轻量**：一次不超过 10 个问题，否则沦为冗长流程。

## 故障排除

### grill-me 不可用

自动降级为 Claude 手工方式。流程仍可继续，只是失去"对抗性质疑"的优化。所有输出格式一致。

### 访谈过长

如果对抗性提问太多或用户反馈过长：
- 可折叠为"用户自己补充遗漏点"，不强制逐个回答
- 或分轮处理：先答关键问题，再答次要问题

### 规划审计卡住

如果发现的问题太多，导致规划看起来"一团糟"：
- 这是正常的，说明规划确实有风险
- Claude 可帮用户优先级化这些问题，不是全部阻塞
- 用户确认"可以接受的风险清单"后，规划仍可推进
